# SÜLD progression simulation

The mathematical model behind `docs/PROGRESSION_BALANCE_SPEC.md`. It runs the game **as it is** (`LiveRules`) and the
**proposed balance** (`ProposedRules`) through the same engine, for the player types and horizons of the directive,
and checks the compliance criteria. **Spec and simulation only — nothing here changes the game yet.**

Every table between `<!-- sim:begin … -->` / `<!-- sim:end … -->` markers is generated by the simulator; do not edit
it by hand. Re-run with:

```
./gradlew :suld-plugin:simulate            # full matrix (~10 min, 4 cores) → this file + audit/progression-balance.json
./gradlew :suld-plugin:simulate -Pquick    # 1 run per class and cell (~1.5 min)
./gradlew :suld-plugin:simTest             # golden + compliance tests (part of ./gradlew check)
./gradlew :suld-plugin:simProbe -Pargs="proposed hardcore baatar 30"   # one trajectory, for debugging
```

## How it works

**Where it lives.** `suld-plugin/src/sim/java/mn/suld/sim/` — a separate Gradle source set that never ships in the
plugin jar and needs no Paper API. It compiles against `suld-api` and a *copy* of the plugin's Bukkit-free content
classes (`SuldContent`, `WorldContent`, `DungeonContent`, `QuestContent`), so the live model reads the real mobs,
regions, dungeons and story, not a transcription.

**What is real code, not a re-implementation:**

| Piece | Real class used |
|---|---|
| Level curve, EXP grants, overflow at 60 | `PolynomialLevelCurve`, `ProgressionEngine.grant` |
| Every loot roll, item, rarity, affix, item level | `LootEngine`, `ItemGenerator`, the real `items/*.json` catalog (proposed: the same engine over a catalog with replaced loot tables and rarity bands — exactly the data change that would be ported) |
| Equipment stats, set bonuses, inactive items, gear score | `Equipment.compute`, `Equipment.gearScore` |
| Selling / salvage / reforge | `ItemEconomy`, `ItemGenerator.upgrade`, `Reforge` cost |
| Skill points (live) | `SkillPoints.total` |
| Login reward, level rewards, ranks | `DailyReward`, `LevelRewards`, `Rank` |
| Live mobs, dungeons, story, world event | the content classes above (boss phases, enrage, completion rewards) |

`Loot` caches 1,500 real rolls per (table, level, tier, class) and samples them, which keeps a 180-day hardcore run to
seconds without changing any probability.

**What is a model (desk calibration, to be replaced by bot/human measurements):**

* **Fight model** (`Engine.fight`): time to kill = mob health ÷ player DPS; damage taken = mob hits × (1 − armour
  mitigation) × hit share (melee 0.55, Мэргэн kiting 0.30, Хүлэгчин 0.45, ranged mobs ×0.7) − regeneration; *danger*
  = damage of one fight ÷ max health; death hazard per fight = 0.012 % + 0.5 / (1 + e^−(danger−1)/0.08). Player DPS =
  (class base + 0.75·(L−1) + gear flat damage) × (1 + ATTACK%) × skill-tree multiplier (+0.8 %/point) × hits/s ×
  crit factor × 1.2 (spells between basic hits). Max health = class base (proposed) or 20 (live) + gear HEALTH +
  0.5/point.
* **Pacing**: kill cycle = time to kill + 7 s to find the next mob (5.5 s Хүлэгчин); 18 kills/min spawn ceiling
  (`RegionSpawner`); efficiency 0.85 (optimal) / 0.70 (typical); town visit 4 min every 45 active minutes; travel
  2–3 min per zone change; dungeons: 4 min setup + 20 s per wave + fights; 5 min to form a group when the dungeon is
  not soloable.
* **Policy**: the player repeatedly picks the activity with the best EXP-equivalent per minute *net of the expected
  cost of dying* (lost play time of the lock, EXP lost, wound), does the story when it is feasible, avoids lethal
  elites/champions solo, and at the level cap works toward whatever its next Ascension rank is missing. Typical
  (casual) players take the second-best option 25 % of the time and accept less danger.
* **Player types**: casual 2 h/day (19:00), active 5 h/day (15:00), hardcore 10 h/day (10:00) — real-time sessions,
  so a death lock costs whatever part of the next sessions it covers. Every row is the median (p50) of the runs, all
  five classes mixed; p10/p90 are in the JSON.

**Calibration sets** (`Profile.Calibration`): low = kill rate ×0.75, dungeon time ×1.3, deaths ×1.5; high = kill
rate ×1.3, dungeon time ×0.75, deaths ×0.6. The 7-day rule is checked at **high**.

**Determinism.** Seeds are fixed (`Sim.SEED`, per cell and run); the cached loot samples are seeded by their key, so
results do not depend on thread order.

**Known limits.** One player at a time (party members are modelled, not simulated); the fight model is a desk model;
combat skill, lag and server events are not modelled; proposed class armour uses existing armour definitions as stat
proxies (same item level and rarity budget) until the class definitions exist; the proposed bands 27–60 use existing
material ids as stand-ins. Calibrating against bot and human sessions (kills/min, deaths/h, dungeon times from the
analytics log) is the first step of the implementation phase — `MANUAL_QA_REQUIRED`.
